# Fares and maps

Every fare/trip setting is defined once in `src/config/tripSettings.ts` (key, type, default, description); `settingModel.getValue(key)` / `getValues(keys)` (one query) return the stored value, or the default when the row is missing or its value doesn't match the type. `src/database/seeds/002_default_settings.ts` inserts them idempotently (`pnpm seed`; existing rows are never overwritten).

`fare.service.ts` `calculateFare` and `calculateWait` (see Trips, boarding) are pure. `calculateFare`: fare = base + km rate + minute rate + wait beyond the grace; the rider pays fare + platform fee + booking fee, the driver earns the fare; money is rounded to 2 decimals. `POST /fares/estimate` is open to any signed-in user (`authenticate` only, it exposes no data). `maps.service.ts` `getRoute` uses Google Directions (`google.service.ts`, the only file that knows Google's API) when `GOOGLE_MAPS_API_KEY` is set and the call succeeds, otherwise haversine distance (`geo.ts`) at `trips.fallbackSpeedKmh`, logging a warning if Google failed. The key is optional (not in CI); tests mock `google.service.js`. Commutes store the start-to-end `distanceMeters`/`durationSeconds`, computed on create and when a start/end coordinate changes.

# Trips

A trip (`trips`, `src/models/trip.model.ts`) is one rider's seat on one date's run of a driver's commute; `driverUserId` is copied from the commute. Statuses: `pending` → `accepted` → `boarded` → `completed`, or `declined` / `cancelled` / `no_show` / `expired`. Routes: `src/routes/trip.routes.ts`, all authorization in `trip.controller.ts`.

- **Seats:** a seat is used only once accepted (`accepted`/`boarded`/`completed`, see `tripModel.seatsTaken`/`seatsLeft`); a pending request takes none. A partial unique index allows one active (`pending`/`accepted`/`boarded`) trip per rider, commute and date.
- **Money:** accepting holds `totalAmount` (`walletModel.hold`: one conditional UPDATE, 409 `Insufficient wallet balance` unless `balance - heldAmount` covers it), boarding turns the hold into one `tripCharge` of the same amount (`capture`), and cancel/decline/no-show `release` it (no ledger row: the balance doesn't change). Amounts must be positive (anything else throws), and releasing more than is held fails `wallets_held_amount_check` and rolls the transaction back — so callers lock the trip row and release or capture only when `trip.heldAmount > 0`, then zero it. Wait time is a separate `waitCharge` debit (capped at what the rider can spend, so never below zero) and the driver's pay a pending `driverEarning` credit into `pendingBalance` (`walletModel.move`, released after `finance.earningsHoldHours`; see wallet-payments). All take the caller's `trx`, so the trip row's `heldAmount`/status change commits with the money: a wallet's `heldAmount` always equals the sum of `heldAmount` over that rider's accepted trips. A partial unique index on `transactions (tripId, type)` refuses a second charge, wait charge or payout for a trip; `wallets.heldAmount >= 0` is a CHECK.
- **Lock order** wherever trip money moves: commute row, then trip row, then rider wallet, then driver wallet — never another order, or two transactions can deadlock.
- **Time:** service time is Ghana (UTC+0, no DST; a Ghana-only assumption). `src/utils/tripTime.ts` (`today`, `isoWeekday`, `departureAt`) is the only place dates and times are worked out, with UTC getters only, so the server's `TZ` never matters.
- **Expiry and the sweep are lazy** (no cron): `tripModel.settleStale(criteria)` runs wherever trips are read or acted on (detail, lists, manifest, cancel, request, every driver action, the commute edit guard). It calls `expireStale` (pending past `expiresAt` → `expired`; safe, a pending trip holds no money), then settles trips whose `scheduledDropoffAt + trips.staleAfterHours` has passed: `accepted` → `no_show` with `cancelledBy: "system"` and the hold released (`reportNoShow`), `boarded` → `completed` with the driver paid (`completeTrip`). Each trip goes through the same locked, status-checked transaction as the manual action, and a 409 from it (someone settled it first) is swallowed, so concurrent readers settle each trip once. No event or activity-log entry for the sweep's own changes.
- Boarding codes (`TR-XXXXXX`) and driver codes (`DR-XXXXXX`) come from `generateCode(prefix)` in `src/utils/code.ts`.
- **Browse** (`GET /trips/available`, riders only): one query in `tripModel.listAvailable` — commute active, running on the date's ISO weekday, driver approved (`carOwnerProfiles.verificationStatus`) with an active, undeleted user, not the caller's own, for today not yet departed, a seat left (same statuses as `seatsTaken`), and start within `trips.availabilityRadiusKm` (bounding box, then SQL haversine). Nearest first, then departure, then id. The date must be today to `trips.bookingWindowDays` ahead. The vehicle shown for a driver is their newest active one, verified first (`joinDriverVehicle`): commutes have no `vehicleId`.
- **Request** (`POST /trips`) checks, each with its own message: rider role, rider profile, commute exists (404), active with an approved driver (409), not their own, weekday, booking window, pickup and drop-off within `trips.routeToleranceKm` of the start-to-end segment with pickup progress < drop-off progress (rounded to the stored 4 decimals), scheduled pickup (departure + progress × the commute's `durationSeconds`, computed and saved via `commuteRoute` if missing) still ahead, available balance ≥ total, and no overlapping active trip on another commute (strictly overlapping: back-to-back is fine), and a seat left (also refused for a pending request, which could never be accepted). The price is `calculateFare` over `getRoute(pickup, dropoff)`, snapshotted on the trip with its `fareBreakdown`. `trips_one_active_per_rider` violations become 409 `You already have a trip on this commute for that date`; a boarding-code clash retries with a new code. A pending request expires at `min(now + trips.requestExpiryMinutes, scheduledPickupAt)`.
- **Accepting** is `tripModel.acceptWithHold` for a pending trip, or the auto-accept branch of `createTrip` when the driver's `autoAcceptBookings` is on — both in one transaction: lock the commute row (`FOR UPDATE`, joined to re-check it's active and its driver approved, active and undeleted — else 409 `This commute is not taking bookings`), then the trip, re-count seats (409 `This commute is full`), `walletModel.hold`, set `accepted`/`acceptedAt`/`heldAmount`. So simultaneous accepts on one commute run one at a time and can't overbook. **Cancel** and **decline** (`closeTrip`) lock the trip, re-check the status (cancel — rider: pending/accepted, driver: accepted; decline — pending only), release a positive hold and zero it; both set `cancelledAt`/`cancelledBy`/`cancellationReason`. The overlap check is a best-effort guard (two simultaneous requests on different commutes can both pass), and pending requests may together exceed the wallet: each accept re-holds atomically.
- **What each viewer sees** (`tripView` in the controller): the boarding code only by the rider; the driver's phone only by the rider and the rider's phone only by the driver, once accepted; the plate once accepted; other riders only as first name and photo (`otherCommuters`); `stops` are the accepted/boarded riders' pickups and drop-offs in progress order with `isYou`, no names — and a rider whose own trip isn't confirmed sees neither, only their own two stops, so requesting and cancelling can't be used to look at other riders. Upcoming (`GET /trips`) = active and not over (boarded, or drop-off still ahead). `GET /trips/:id` is for the rider, the driver, or an admin with `trips: read`; `GET /trips` lists a rider's own trips or a driver's commutes' trips. Activity logs store the view with neither code nor phone.
- **Driver side:** `POST /trips/:id/accept` and `/decline` are for the trip's driver only (403 for anyone else, admins included); `findTripForDriver` settles the trip first, so a stale request answers 409 `Can't accept a trip that is expired` (the same message if it expires under the lock). An accept whose hold fails answers 409 `The rider's wallet no longer covers this trip` and leaves the request pending. `GET /commutes/:id/trips` (the manifest, via `findCommuteFor`: the driver or `commutes: read`) lists a date's trips (default today, any date) soonest pickup first, with the rider's phone only for seat statuses and only to the commute's driver (not an admin), never a boarding code, plus `capacity`, `seatsLeft` and `stops` (the route sheet: accepted/boarded riders with first names; `stopsOf` in the controller is shared with `tripView`). All three share `tripActionLimit` (120 per 15 min per account).
- **Commute edit guard:** `PATCH /commutes/:id` answers 409 when it changes a coordinate, `departureTime` or `recurrenceDays` (compared to the stored values: coordinates rounded to the column's 6 decimals, days as a set) while, after expiring the commute's stale requests, `tripModel.hasActiveTripsFrom(id, today())` finds a pending/accepted/boarded trip; address text, capacity and `isActive` stay editable (seats left clamp at 0 if capacity drops below the seats taken). Best effort like the overlap check: a request can slip in between the check and the update. `DELETE` is refused by the trips FK whenever any trip exists.
- **Boarding** (money moves only at the scan): the rider's app `PUT /trips/:id/location` (their own accepted trip, from `boardingEarlyMinutes` before the scheduled pickup; stores `riderLat/Lng/LocationAt`, not activity-logged, `tripLocationLimit` 300/15 min). The driver `POST /trips/:id/arrived` with their location (accepted, inside the window, within `trips.boardingRadiusMeters` of the pickup; only the first mark sets `arrivedAt`, a repeat returns 200 unchanged with no event or log). `POST /trips/board` (`{ code, lat, lng }`, drivers, `tripBoardLimit` 60/15 min against code guessing) finds the trip by `boardingCode` **and** `driverUserId = caller` — anything else is the same 404 `No trip found for that code`, so codes can't be probed; the scanned `code` is redacted from the activity log's request body and from `httpLogger`, which also blanks `data.boardingCode` in every logged response (`loggableResponse`) — then checks: accepted, now inside `scheduledPickupAt − boardingEarlyMinutes … + boardingLateMinutes` (never `tripDate`: a pickup can fall after midnight), driver within the radius of the pickup, the rider's location no older than `trips.locationMaxAgeSeconds` and within the radius of the **driver**. `tripModel.boardTrip` then, in one transaction (trip row, then rider wallet): re-checks `accepted` and that `heldAmount === totalAmount` (else a plain `Error`: a broken hold must not board free), `capture`s it as the `tripCharge`, debits a positive wait charge as `waitCharge` (capped at `spendableIn`: whatever the wallet can't cover is waived), and sets `boarded`/`boardedAt`/`boardingLat/Lng`/`waitMinutes`/`waitCharge`, `heldAmount = 0`, `driverEarnings = fare + waitCharge`. Wait (`calculateWait`): 0 without an arrival mark, else `floor((boardedAt − max(scheduledPickupAt, arrivedAt)) / 1 min)`; the minutes past `fares.waitGraceMinutes` at `fares.waitPerMinuteRate`, no fees, all to the driver; the charge (and so `waitCharge`/`driverEarnings`) is capped at the rider's spendable balance under the wallet lock, so a wallet never goes below zero.
- **Complete / no-show:** `POST /trips/:id/complete` (the driver; `tripModel.completeTrip`: lock the trip, re-check `boarded`, credit `driverEarnings` as a pending `driverEarning` into the driver's `pendingBalance` with `availableAt = heldUntil(completedAt)`, record `platformFee + bookingFee` as the platform's `platformFee` row, `completed`/`completedAt`). `POST /trips/:id/no-show` (the driver; accepted, and only from `scheduledPickupAt + boardingLateMinutes`, when the scan window has closed, else 409 with that time): `reportNoShow` via `closeTrip` releases the hold, `no_show`, `cancelledBy: "driver"`, reason `Rider did not show up`. The status re-check under the trip lock plus `transactions_one_per_trip_type` make a double scan charge once and a double complete pay once; a scan racing a cancel or no-show ends in exactly one of them. All three and arrival use `tripActionLimit` except the scan; each is activity-logged (`trip.arrive`, `trip.board`, `trip.complete`, `trip.no_show`).
- Socket events: `trip:requested` to the driver on every request (status pending or accepted), `trip:cancelled` to the other party, `trip:accepted` / `trip:declined` / `trip:driver_arrived` / `trip:boarded` / `trip:completed` / `trip:no_show` to the rider.
